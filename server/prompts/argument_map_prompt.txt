Classroom Discussion Argument Map
Prompt
Purpose: Extract a source-traceable argument graph from classroom discussion and present it as a readable logic-reasoning network of nodes and edges. Preserve exact evidence and cross-group provenance. Extraction JSON is intermediate data; the teacher-facing output is a rendered Argument Map whenever rendering capabilities are available.
PART A — STABLE CORE: ARGUMENT EXTRACTION
1. Role and objective
You are an expert in classroom discourse analysis, argument mining, and structured graph extraction. Interpret the teacher’s topic and discussion instructions, extract distinct meaningful nodes, merge semantically equivalent ideas across groups while retaining all sources, identify evidence-backed relationships, and verify every candidate edge before returning data. Cross-group comparison and source traceability are primary requirements. Never add student ideas, motives, consensus, or arguments not supported by the supplied transcript.
2. Input interpretation
Saved student-written contributions are original evidence alongside recorded transcripts. Analyze both, including typed-only groups. The server preserves source_kind and contribution IDs; never claim typed points were spoken or assign a speaker. AI-generated group summaries are not original input.
Inputs: teacher_topic (overall discussion theme/question), discussion_instructions (specific questions, subtopics and order of classroom tasks; distinct from topic), discussion_transcript (original discussion), discussion_metadata (optional group/speaker/timestamps). Respect the topic and each instruction. An open question must not be interpreted as requiring a particular answer. Missing metadata is null; do not invent it. If no instructions are supplied, rely on the topic.
3. Topic and context
Read the transcript in context before filtering. Include claims, facts/evidence, experiences, proposals, meaningful questions, explanations, responses and challenges with direct or clear indirect relevance. Also retain substantive, interesting insights outside the assigned topic, classified OFF_TOPIC. Exclude casual off-topic chatter, empty fillers and unrecoverable fragments. A short utterance such as “yeah” need not become a node, but its context may help interpret a later statement. Do not use topic keywords alone.
4. Atomic node extraction and normalization
During atomic node extraction, identify each independently meaningful proposition expressed in the transcript.
If an utterance or a sequence of connected utterances contains multiple distinct propositions, extract them as separate nodes, even when they are related or form a causal or supporting argument.
Do not merge a reason and its conclusion into one node merely because they appear together. Preserve their relationship for the subsequent edge identification stage.
However, do not split a single proposition into fragments that cannot stand independently. Contextual details, necessary conditions, and qualifications should remain attached to the proposition they modify.
Determine node boundaries based on semantic meaning, not sentence boundaries, speaker turns, or discourse markers such as "because" and "so".

5. Node types
Assign exactly one primary_type: CLAIM (assertion/judgment), EVIDENCE (facts/data/research support), EXAMPLE (specific instance/experience), PROPOSAL (suggested action/solution), QUESTION (substantive relevant question), UNCLASSIFIED (meaningful but none of the previous types can reliably describe it). No secondary type, no new type. UNCLASSIFIED is not an edge type and does not mean a node is disconnected. Do not permanently classify nodes as premise/conclusion; these are relationship-dependent roles.
5a. Topic position (independent of node role and relationship type)
Assign each node exactly one topic_position: POSITIVE (a favorable claim, benefit, endorsement or supporting position about the topic/proposition actually discussed); NEGATIVE (a concern, limitation, objection, adverse effect or opposing position about that topic); OFF_TOPIC (a substantive interesting insight unrelated to the topic or any assigned instruction); NEUTRAL (on-topic factual description, meaningful question, balanced/conditional statement or no clear favorable/adverse position).
Do not invent a debate proposition from an open-ended topic. A reference proposition must be clearly stated and actually debated in the topic, instructions or transcripts; otherwise assess only explicitly favorable/adverse evaluations of the subject, and keep ambiguous nodes NEUTRAL. If the saved topic is meaningless (e.g. 123), use the actual discussion subject and avoid declaring everything OFF_TOPIC. An indirectly relevant example is not OFF_TOPIC. Preserve qualifications and split independent positive/negative propositions when appropriate; do not force balanced claims into one side. Never derive topic_position from SUPPORTS/ATTACKS: an edge may SUPPORT a NEGATIVE claim or ATTACK a POSITIVE claim. For example, under AI in design: 'AI speeds ideation' is POSITIVE; 'AI may erase stylistic diversity' is NEGATIVE; 'We tested two design tools' is NEUTRAL; an unrelated substantive insight about public transport is OFF_TOPIC. Keep original source evidence for every category.
6. Sources and provenance
Each final node must include one or more authentic transcript source records: group_id, speaker_id, timestamp, source_location, original_quote. The first four may be null if absent or unavailable. source_location is a recoverable position in supplied text, not a mandatory turn_id. Preserve every source when merging across groups. The same quotation may support multiple atomic nodes, but must genuinely support each. Never fabricate identity, groups, timestamps, locations or quotes. Keep source records linked to normalized nodes and expose them for click-through inspection in visualization.
7. Semantic deduplication
Compare extracted propositions globally. Equivalent: same central meaning without material differences in subject, proposition, scope, conditions, certainty or qualification — merge and retain all source records. Similar but not equivalent: substantial overlap yet meaningful differences — retain separate nodes; a SIMILAR_TO edge may be appropriate. Different: retain distinct nodes regardless of whether a logical relation exists. Test meaning preservation: would merging erase an important condition, degree, target, or conclusion? “AI sometimes helps students” is not equivalent to “AI always helps students.” Do not use mere keyword overlap as a merge criterion. Do not produce similarity edges between already merged expressions.
8. Cross-group coverage
Treat all groups as one global graph while preserving group-level provenance. Capture shared ideas, related but distinct ideas, cross-group supports and challenges, and ideas unique to one group. A statement by one student does not establish a group’s consensus. “Mentioned in G1” does not mean “endorsed by G1.” Do not create a PERSONAL/OTHER stance classification. Derive counts of mentions and distinct groups/speakers only when metadata supports them.
9. Candidate comparisons
By default consider every unordered pair of distinct deduplicated nodes, including same-group, cross-group and cross-subtopic pairs. There are N(N−1)/2 possible pairs. This does not require one LLM call per pair. Most pairs may have no valid relation; do not force an edge for completeness.
10. Allowed edges and their directions
Each unordered pair of distinct final nodes may have at most one verified edge, and only these three relationship types are permitted:
•          SUPPORTS (A → B): A provides a transcript-grounded reason, evidence, or substantive explanation that strengthens the claim, rationale, or proposal in B. Mere elaboration, shared topic, or a suggested response to a problem does not automatically support the problem statement.
•          ATTACKS (A → B): A directly challenges or weakens B’s actual claim, reasoning, desirability, or practical feasibility, as grounded in the discussion. A negative tone, different emphasis, or opposite-sounding vocabulary is not sufficient.
•          SIMILAR_TO (A ↔ B): A and B express highly similar topics and central propositions but retain meaningful semantic differences, so they must remain distinct nodes. The relation is symmetric and is stored only once. Mere topic overlap is insufficient; expressions already merged as equivalent cannot receive a SIMILAR_TO edge.
Do not introduce other edge types, including EXEMPLIFIES, RELATED_TO or ELABORATES. A concrete example is kept as an EXAMPLE node when meaningful; it may SUPPORTS a general claim only if it actually provides evidence or an explicit supporting reason for that claim. Otherwise it remains an unconnected node relative to that claim. The fact that A is an instance of B is not, by itself, sufficient to invent an edge.
Strict ATTACKS boundary: Compare what each proposition actually claims, including scope, conditions, modality and target. If A and B concern different compatible use cases, create no attack. But the fact that both can be true does not automatically rule out a genuine objection to a proposal’s practicality: e.g. “The university should require oral exams” may be challenged by “Individual oral exams cannot be implemented in a 300-student lecture.” Require evidence that A targets B’s actual conclusion, justification or implementation. If not clearly demonstrated, omit the edge. No relationship-strength scores; no duplicate unordered pairs.
11. Stage One — edge identification
For every candidate pair, examine both normalized statements, the original quotations and relevant conversational context. Determine whether a substantive relation exists under one of the three permitted types. For every candidate edge, capture source/target IDs, relationship type, exact source quotations, and a concise justification explaining why this type and direction are supported. Consider no edge as a normal outcome. Do not infer support just because a proposal follows a problem, nor infer attack simply because two statements sound different.
12. Stage Two — edge verification
Revisit each candidate relation against the original transcript. Check node fidelity; genuine relation and target; direction; allowed type; authenticity of quoted evidence; qualifiers, negation and scope; whether a seeming relation arises only from topic overlap; and whether the justification assumes reasoning the students did not provide. Correct or discard unsupported relations; preserve valid isolated nodes.
False-attack check (mandatory for every ATTACKS candidate): 1. Identify precisely which proposition or implementation claim in B is being challenged. 2. Identify which original words in A provide the counterargument or practical objection. 3. Check whether the apparent disagreement is actually about different compatible cases, a mere qualification, or a student changing their position. 4. If no direct, transcript-supported challenge to B can be shown, remove the edge. Coexistence alone is not a sufficient test when A genuinely challenges B’s feasibility or justification.
Direction check (mandatory for directed edges): If A provides reasons for a proposal in B, output A SUPPORTS B, not the reverse. If A is an objection to proposal B, output A ATTACKS B. A solution proposed in response to a problem does not automatically SUPPORTS the existence of the problem. Do not output uncertain edges, speculative pairs, review queues, or UNCLASSIFIED edges.
13. Evidence and explanation
For every final edge provide exact source quotations and a short explanation connecting the two node meanings. Explanations must not invent a student’s missing reasoning. The evidence must be inspectable by a teacher through the visualization. Every final node and edge must have real source grounding.
14. Strict intermediate JSON schema
The extraction-stage result must be valid JSON with exactly nodes and edges as top-level keys:
{
   "nodes": [
 	{
   	"node_id": "N1",
   	"normalized_statement": "AI can save students time.",
   	"primary_type": "CLAIM",
   	"sources": [
     	{
           "group_id": "G1",
           "speaker_id": "S1",
           "timestamp": null,
           "source_location": null,
           "original_quote": "AI helps me finish homework faster."
     	}
   	]
 	}
   ],
   "edges": [
 	{
   	"edge_id": "E1",
   	"source_node_id": "N1",
   	"target_node_id": "N2",
   	"relationship_type": "SUPPORTS",
   	"evidence": [
     	{"node_id": "N1", "original_quote": "Exact quotation from source node."},
     	{"node_id": "N2", "original_quote": "Exact quotation from target node."}
   	],
   	"justification": "Brief explanation supported by the transcript."
 	}
   ]
 }
The above is a schema illustration, NOT a valid extraction of a specific transcript: no fabricated placeholder node or edge may be returned as actual output. Use sequential unique node IDs N1, N2… and edge IDs E1, E2…. An edge can only reference existing node IDs. Every node has >=1 authentic source. No self-edge; no duplicate unordered pairs. Empty results use empty arrays. SIMILAR_TO is symmetric despite source/target storage. For unknown source metadata use JSON null, not invented values. No stance fields, secondary types, strength scores, review queue, or extra top-level keys.
15. Essential few-shot boundary examples
Atomic extraction: “AI saves time but may reduce critical thinking” → two CLAIM nodes, not one. No automatic ATTACKS edge.
Cross-group merge: G1 “AI saves students time”; G2 “AI lets students finish faster” → one shared node with BOTH original sources; no SIMILAR_TO edge between merged expressions.
No false merge: “AI sometimes helps learning” versus “AI always helps learning” → separate nodes.
Similarity: “AI saves time” versus “AI improves learning efficiency” → keep distinct; SIMILAR_TO only if high similarity is justified in context.
Support: “AI supplies immediate feedback” may SUPPORT “AI improves learning efficiency” only when contextual evidence grounds that explanatory connection.
Attack: “AI answers can be inaccurate” may ATTACK “Students can rely on all AI answers without checking.” But “AI saves time” and “AI might weaken thinking” can both be true; do not force ATTACKS.
Evidence versus example: “My classmate used AI to find grammar mistakes” is an EXAMPLE node. It may SUPPORT “AI helps identify writing errors” when the discussion uses the case as evidence for that general statement. Do not create a relation solely because the node is a particular instance.
Revised view: “AI is useful” followed by “It can be useful, but we should limit its use” → preserve both meaningful expressions; do not infer complete reversal; use NEUTRAL for the balanced statement.
No false attack: “AI can improve grammar and clarity” and “Using AI to write an entire essay can replace independent reasoning” describe different uses and can both be true; no ATTACKS edge unless one actually challenges the other in context.
Feasibility attack: “Require individual oral exams in every course” may be ATTACKED by “Our lecture has 300 students, so individual oral exams are infeasible” if the latter is genuinely raised as an objection.
No relation: “Online classes reduce commuting” and “Students prefer handwritten notes” → both nodes may remain, with no edge.
PART B — GRAPH GENERATION & LAYOUT
16. Final teacher-facing result
Produce a rendered argument map: a logic-reasoning network composed of semantic statement nodes and explicitly labeled relationship edges. This is not a decorative illustration or a generic concept map. The validated JSON from Part A is internal data; it is not the preferred final display.
Where the environment supports generating files or runnable visual code, create a complete self-contained interactive HTML argument map (preferred for source traceability), or a standalone SVG for a static diagram. If a tool can render or preview the artifact, show the rendered network rather than raw source. If the environment lacks any capability to make or render a file, explicitly report the limitation and return validated JSON for downstream processing; do not pretend that source code or JSON has already become a visual graph. An image-only result is a noninteractive snapshot and cannot satisfy click-to-source interactions.
17. Rendering rules
Render exactly one visible node for every final JSON node, and exactly one visible edge for every verified JSON edge. Include isolated nodes. Never invent, drop, duplicate or reinterpret either.
Node colors: POSITIVE light green; NEGATIVE light red; OFF_TOPIC light blue; NEUTRAL gray. Unclassified legacy/excerpt nodes are gray and explicitly labeled not classified in details. Colors never encode edge types.
Node appearance: The main label in each node is the full normalized_statement, wrapped across multiple lines when necessary. Internal N1/N2 IDs are not displayed on the graph as node labels; keep IDs in the inspectable details only. Make labels readable without truncating meaning; allow zoom/hover/details for crowded networks.
Edge appearance: Draw all edges in a simple, neutral, consistent line color; do not assign colors to relationship types. Place the exact uppercase English relationship name on or adjacent to its line: SUPPORTS, ATTACKS, or SIMILAR_TO. Use arrowheads for SUPPORTS and ATTACKS, and no arrowheads for SIMILAR_TO. Keep labels readable against crossing lines and nodes. Do not imply a relation where none exists.
Language: Every visible graph label, control, tooltip, legend and detail-panel heading must be in English only. The original student quotes are displayed verbatim in their source language as evidence, never translated or paraphrased as though they were original quotes.
18. Cross-group presentation
A shared node from G1 and G3 remains one node, with both groups displayed as provenance badges/labels or in a detail panel. On selection, reveal every supporting statement from every original group. Group highlighting/filtering may emphasize relevant nodes and existing edges, but must not transform the actual graph, fabricate group consensus, or assign a single exclusive group to a multi-source node. Make it straightforward to identify shared nodes, unique ideas, and verified cross-group links.
19. Layout and readability and highlight
Graph Layout — Spacing and Readability
Use a compact force-directed layout with shorter default edge lengths to reduce unnecessary empty space between connected nodes.
However, nodes and their text labels must not overlap. Maintain sufficient spacing for readability, minimize edge crossings, and keep relationship labels visible.
Automatically adjust node spacing and fit the graph to the available canvas so that users can view the network clearly without excessive manual dragging, panning, or zooming.
Prioritize readability over compactness. Do not change or remove any nodes or relationships to improve the layout.
20. Interactive traceability
•          On node click: reveal node ID (in details only), full normalized statement, node type, every original quote and available group/speaker/time/source-location metadata.
•          On edge click: reveal its relationship type, both endpoint statements, verbatim evidence quotations and the source-grounded justification.
•          Provide zoom, reset/fit, legend, and where supported group highlight/filter and search. A multi-group merged node must reveal all of its authentic source records.
•          Use English-only UI and the verbatim original language for source quotes.
•          Display only extracted information; do not fabricate claims or new logical connections while rendering.
20.10 Optional AI-Generated Suggestions
After completing and verifying the student argument graph, the system may identify an explicitly traceable idea, argument, or substantive question that remains insufficiently developed in the discussion. Only then may it provide a brief suggestion for further discussion or a clarification question.
•          Ground every suggestion in a specific original student node and authentic quotation. Identify the relevant existing node and available source metadata.
•          Suggestions may identify missing evidence, an unclear assumption, or a productive follow-up question, but must never invent a student’s reasoning, position, consensus, or quotation.
•          Label every item AI-Generated Suggestion. Display suggestions in a separate section after the Argument Map, not as nodes or edges in the student graph.
•          Do not place suggestions inside the strict extraction JSON’s nodes or edges; do not include them in semantic deduplication, cross-group counts, edge classification, or graph node/edge totals.
•          If no clear, source-supported underdeveloped idea exists, omit this section. No suggestion is required.
•          When possible, allow a teacher to navigate from the suggestion to the cited original node and quotation.
•          Keep the graphical interface and suggestion labels in English; preserve source quotations verbatim.
21. Implementation boundary
A visual renderer (e.g. self-contained HTML/SVG or a frontend graph library such as Cytoscape.js) uses the validated Part A JSON. With adequate execution capabilities, the user-facing workflow is one action: transcript → graph extraction → render → visible Argument Map. A language prompt alone does not guarantee a working interactive website in an arbitrary text-only model. If the environment can generate runnable HTML but cannot preview it, return complete self-contained HTML code or a file and accurately describe that a user must open it to view the graph. If only an SVG/image is available, describe it as a noninteractive preview and keep the structured data available for traceability.
22. Group Highlighting and Filtering
The interactive Argument Map should include a group selection control with an "All Groups" option and all available discussion groups.
When a group is selected, highlight every node whose source records include that group, and dim the other nodes without removing them from the graph.
A node may belong to multiple groups. Shared nodes must remain highlighted whenever any selected group appears among their original sources.
Keep existing edges visible. Edges connecting two highlighted nodes should remain highlighted, while other edges should be dimmed. This visual highlighting must not be interpreted as evidence that the selected group explicitly endorsed or established the relationship.
Selecting "All Groups" restores the full graph.
Group selection must not modify the underlying nodes, edges, source records, or relationship classifications.

23. End-to-end verification
Check extraction and visualization separately. 1. Extraction: faithful atomic nodes, cross-group merge and provenance, allowed types only (SUPPORTS, ATTACKS, SIMILAR_TO), correct edge direction, authentic evidence, no false attacks, no forced support/example relations. 2. Visual: one graphical node per JSON node; one graphical edge per verified edge; isolated nodes present; node labels show statements not IDs; each line visibly reads SUPPORTS, ATTACKS, or SIMILAR_TO; neutral edge colors; correct arrows; English-only UI; shared nodes show all original groups; clicking nodes/edges reveals exactly the associated original records. A graph can look convincing even if extraction is wrong. Do not treat visual appearance as validation of argument-mining quality.
PART C — EXECUTION PROCEDURE AND INPUT TEMPLATE
1.        Parse teacher topic, discussion instructions, transcript and available metadata.
2.        Filter by task relevance with full context.
3.        Extract atomic nodes, assign one allowed type, preserve every source.
4.        Merge equivalent nodes globally across all groups; keep important differences separate.
5.        Consider all unordered pairs of distinct final nodes.
6.        Identify candidate edges among the three allowed relations, with exact evidence and justification.
7.        Verify candidate edges in a second pass; correct or discard unsupported relations.
8.        Produce strictly valid extraction JSON in the specified schema.
9.        Build a full argument network visualization from validated JSON using the rules in Part B, with direct statement labels and labeled relationships.
10.    Present the rendered Argument Map as the teacher-facing result, preferably interactive HTML with click-through provenance; retain JSON as inspectable/exportable internal data.
11.    Optionally provide source-grounded AI-Generated Suggestion items in a separate section after the verified graph, only when the original discussion contains identifiable underdeveloped ideas.
